# Probing stateful and remote surfaces

Deep-probe pitfalls for dogfood runs against products that hold state outside the
process under test: queues, sync/reconciliation plans, job registries, network peers. The SKILL.md pitfall list carries the always-on rules; consult this file
when the target's real use moves state on a server, a store, or a peer.

- **Fire two jobs with the IDENTICAL job identity at products that derive named resources from identity (container names, keys, log objects).** A deterministic name plus no idempotency makes the loser record an undiagnosable failure (docker exit 125, empty log) while the winner's output overwrites the shared evidence object keyed by the same attempt — the finding is the collision contract (first-class conflict outcome, per-execution log keys, captured stderr), not either job's individual result.
- **A sync/reconciliation plan computed from a cached or eventually-consistent listing silently no-ops on real changes — and its decision ledger can record values that never coexisted.** When the planner's LIST comes from a cache (a serving layer's dir-cache, S3 replicas), an external edit followed by an immediate sync reports '0 to transfer' with no staleness hint; and a ledger row written from a post-transfer re-stat (e.g. after mtime alignment) can carry local==remote values that never existed as separate states. Test the staleness path deliberately (edit behind the cache, sync immediately), and check whether ledger rows capture DECISION-time values or post-write values — the latter are unfalsifiable. A second, sharper shape: when the PLANNER and the EXECUTOR read the same attribute (mtime) from DIFFERENT protocol surfaces (LIST vs HEAD), the aligned steady state is unreachable — the executor aligns to one surface's value while the planner compares against the other's, so every run re-transfers and re-logs forever. Curl both surfaces for the same object on your test server before trusting any sync verdict; disagreement between them is its own finding (and can be the test server's defect, not the product's — say which in the row).
- **When a CLI reports an opaque failure against a network service, strace its socket writes before reading source.** `strace -f -e trace=writev -s 400 -o /tmp/x.log <cmd>` captures every HTTP request the binary actually makes (path, headers, checksum flags) in order; run the failing verb alone to shrink the log, then curl each captured request yourself and compare every metadata surface the protocol exposes. A swallowed client-side error that produces no local error text is the finding, the strace capture is the evidence.
- **A resource absent from a queue-style retrieve may be LEASED, not missing — check the queue stats before believing an empty inbox.** Retrieve-and-hold semantics hide an unacked item from the next retrieve for the lease duration while the stats endpoint still reports it (`leased_count:1, oldest_age_ms` growing); a first-time user reads this as data loss. Drive the lease: retrieve, DON'T ack, re-retrieve, then read stats — and file the response-shape gap (an empty retrieve should say WHY it is empty) rather than accepting silence.
- **A library-only module with injected seams is still real-use surface — drive it through its public API with a small injected fake, not through its test suite.** Import the module, register a fake adapter/transport, and time the hot verb directly: a fresh import alone can cost hundreds of ms of cold-start while the warm call is sub-ms — measure BOTH before filing a PERF row. This also exercises the negative paths tests stub past: config refusals (a zero/negative TTL must be a typed InvalidConfig, not a silent accept), expiry-then-refetch, and ceiling refusals. A refusal firing with the right exception type is a PASS; no row unless a real user would notice the number.
- **On a re-proof pass file NO new rows — design the run's angle so pending rows' premises get tested against current state, and let the dogfood-log entry be the artifact.** A quiet run where the artifact is accurate is a SUCCESS; re-filing a known finding to show output devalues the board. Cross-check integrity surfaces against each other (health/check script WARN list vs the live deployment), and when the check's WARN names its own fix command, RUN it — an operator action the product itself prescribes (e.g. a deploy-sync script) is legitimate real use, provided it changes deployed copies only and never repo code.
- **A client shim can turn a rejected backend action into success-shaped output — diff the shim's rendered text against the BACKEND's reply object before grading an error path as honest.** A bridge correctly returned `{ok:false, error:'paused — call resume first'}`; the shim's formatter read only the payload fields it expected (`screen`, `player`) and printed `stepped. screen=None tile=None` — a success shape whose Nones are the only clue anything went wrong. Rule: for every wrapper (MCP tool, RPC shim, CLI subcommand) over a lower protocol, drive each backend rejection class through it and check the rendered text carries the backend's error verbatim; a formatter that drops the error field converts a correct fail-closed backend into a misleading client, and the finding is the shim's dropped field, not the backend. When the shim's own doc documents the lossy formatting, cite the doc line in the row — documented-but-misleading is still a usability finding (P3), because the client sees success-shaped text regardless.
- **Multi-request services that close the connection after one exchange answer a reused socket with EMPTY replies, not errors — probe each request on a FRESH connection before filing a protocol defect.** If a client holds one connection and sends several line-delimited requests, every request after the first can return an empty line while the SAME request on a fresh connection answers fine — read that as a per-connection design (read one request, reply, close), not a server hang. Re-read the client's own transport before interpreting your probe's empties: a manual socket test that pipelines requests on one connection tests the wrong contract, and the real finding (if any) lives in how the client itself manages connections.
- **Probe a containerized product's store THROUGH the container with the product's own dependency tree — the volume is host-unreadable and the runtime image has no sqlite3 and no devDependencies.** A compose volume (`/var/lib/docker/volumes/<proj>_<vol>/_data`) is root-owned on the host, `docker exec <c> node -e "require('better-sqlite3')"` dies MODULE_NOT_FOUND, and there is no sqlite3 binary: resolve the module from the pnpm store — `ls` the container's `node_modules/.pnpm | grep -i sqlite` to name the version, then `docker exec -w /app/node_modules/.pnpm/better-sqlite3@<ver>/node_modules/better-sqlite3 <c> node -e "const D=require('./'); ..."` and open the DB `{readonly:true}`. Read the schema FIRST (`SELECT sql FROM sqlite_master WHERE name='...'`): column names drift from the API's vocabulary (a config JSON blob vs the dedicated column the endpoint prose implies). Reconcile endpoint numbers against raw rows before trusting any summary: wins-by-winner sums vs the stats endpoint, a NULL census on the disputed column, and per-row-class splits — legacy/mock rows are identified by a `config LIKE '%mock%'` marker, not a dedicated column, and when all-report-games minus store winners equals exactly the mock-row count, the endpoint silently drops one row class: verdict 'partially fixed', not 'fixed'.
- **A bootstrap secret printed once at creation is unrecoverable from the store — the store keeps only the hash.** When a resumed run must re-authenticate against a scratch instance whose first-admin/bootstrap key was never saved, do not re-bootstrap: grep /tmp artifacts for the printed secret candidates first (`grep -rhoEh '<key-prefix-pattern>[0-9a-f]{32,}' /tmp/*.json /tmp/*.txt /tmp/*.log`) and match each candidate's sha256 against the stored hash in a loop; only when no candidate matches, insert a NEW key row directly into the scratch DB — sha256 of your raw key as `key_hash`, its first 8 chars as `key_prefix`, the admin scope — because the auth validator queries by (key_prefix, key_hash) and never needs the original. This works on scratch/throwaway instances only; production key rotation belongs to the product's own flows.
- **Drive every documented CREATION path, not just every read surface — the same product can build the "same" object differently per entry point.** A game created from the web modal and the identical-looking game created via the API/CLI ran different engine wirings in one product: the API-created instance served live state on every surface while the UI-created instance returned a frozen SETUP snapshot on the state endpoint and a live roster on the list endpoint at the same minute — every UI reader stayed blind while the engine played on. Create once per surface (UI modal, CLI, raw POST), tag each created object's id, and diff EVERY read surface (list, detail, state, WS, reports) per instance before declaring the object model consistent; a read surface that is correct for one producer and stale for another is its own row, scoped to the creation path. Corollary: before interpreting a creation anomaly, read the server's own logs — one UI 'New Game' header button can auto-create a game on click while the modal's Create makes the second, so 'I clicked once, two games exist' is a UX row, not a duplicate-object bug.
- **Diff the writer paths on their DERIVED state, not just their API response — a sibling create path that skips a derived-write (search indexing, metadata stamping) fails SILENTLY because reads return a calm 200 with 0 results, never an error.** When a product has two ways to create the same record (direct-create endpoint vs ingest pipeline), post the SAME payload through both and diff downstream state: the derived search index row (count by a unique marker string, not the response body), the metadata blob the automation/rules engine grades, audit rows. One real product's ingest path indexed to OpenSearch and stamped `source` metadata while its sibling create endpoint did neither — automation rules evaluated 0 matches and searches returned empty for every direct-created record, with no 4xx anywhere; only the marker-string count on the raw index (`GET /<index>/_count?q=<marker>`) separated the paths. A silent 200-empty read is WORSE than a 4xx (nothing hints the data was never indexed), so scope the row to the missing derived-write and its silent read contract.
- **Keep in-container probes as HOST files and `docker cp` them in; do not hand-build Python through `docker exec` -c/heredoc chains.** Two frictions recur: executors block inline `python -c` scripts, and imports inside the container need the app's own sys.path (`sys.path.insert(0, '/app')` or run with `-w /app`) — a ModuleNotFoundError from a probe is the probe's path problem, not the product's defect. Read the target function's ACTUAL signature before calling it (`grep -n 'def f'` then sed the function head): guessing positional order costs a retry per guess, and result-object field names vary from the log format (`evaluated_rules` in the log line vs `evaluated_count` on the dataclass).
