# Dogfood perf-probe pitfalls

Depth for the dogfood skill's Step 2b. Rules here apply when MEASURING; the perf law itself (no optimization without a measurement, no claim without re-measurement) stays in skill `coding-hermes-perf`.

- **py-spy raw profiles: `py-spy record -f raw -o raw.txt -- <cmd>` — ONE `-o`** (a second `-o` silently overrides the first and you lose the file); `py-spy top` has NO `--duration` flag. From a folded file, self-time per FUNCTION = sum sample counts by the last `;`-separated frame (a 10-line python Counter over `stack.rpartition(' ')` + `split(';')[-1]`) — sorting whole lines ranks STACKS, not functions, and double-counts callers.

- **Benchmark with a real monotonic clock, not shell `date` arithmetic.** `t0=$(date +%s%3N)` between two shell invocations produced millisecond numbers off by 6+ orders of magnitude (subshell spawn cost + `%N` support varying by `date` flavor) — the garbage timing then read as a pathological latency that did not exist. Time from inside ONE process: `hyperfine`, or a python `time.monotonic()` wrapper around the subprocess. Shell `date` deltas are for second-granularity stopwatches only.

- **Attribute latency to the external dependency with a DIRECT control arm of that dependency.** When an endpoint that calls out to an LLM/API costs ~1s while health answers in 5ms, curl the upstream endpoint DIRECTLY with the same model/payload and compare: direct ≥ endpoint means the endpoint is bounded by provider RTT, not by the server — that is documented blocking behavior, never a PERF row.

- **A repeat-run perf probe must VALIDATE its scaled fixtures before interpreting numbers.** When measuring scaling (e.g. a quadratic-scan claim), build the synthetic boards with UNIQUE row ids (e.g. `SCALE-000001…`) rather than `head -N` of the real board — with a small real board, `head -4500` still yields 45 rows and the 'no scaling' conclusion describes a test that never ran. Give every latency FINDING a CONTROL ARM measured the same way on the same path (a fast sibling query/endpoint over the same data): but when the target is a LIVE tracked daemon, page the whole surface FIRST to localize: per-page timings usually pin the cost to one hot render path (one 1-10s landing page amid 0.001-0.2s siblings), then capture the profile DURING the hot request — launch the request in the background (subshell `&`, not shell job control which unattended surfaces block) while a timed `GET /debug/pprof/profile?seconds=N` runs, and read the result with `-top -cum`: the flat view is noise-dominated (per-frame `Syscall6`, JSON and sqlite internals) and cum view names YOUR package's handler frame holding the cost — that function name + file:line is the anchor the PERF row needs., and keyword-vs-semantic timing on one namespace is what turns 'search felt slow' into an actionable finding (e.g. 0.4s vs 15-30s). Sanity-check the fixture (row count, unique-id count) against the intended N before reading hyperfine's output, then file the measured curve (or its absence) as the cross-evidence note on the existing row — no duplicate PERF row for a claim another lane already filed.

- **For a compiled daemon with no HTTP profile endpoint, `perf record` attaches to the LIVE pid and the workload drives itself from another shell.** `perf record -F 199 -p <daemon-pid> -- sleep 10` in a background terminal, then run the measured traversal/request loop from a second call during the window. Never re-launch the binary under the profiler — a profile of a fresh start measures startup, not the steady-state path users pay for. Without root, kernel samples come back unresolved; the user-space shares still rank the hot frames. Read `perf report --stdio --no-children` and sum the percentages into CLASSES before quoting (e.g. '≈52% std::path parse/compare inside <fn>, ≈13% linear scans over <map>') — raw top-N lines with template-noise symbols are unreadable and invite eyeballing, the thing the perf law forbids.

- **Pair a macro traversal timing with a micro per-op timing before attributing proxy-surface slowness.** Over a FUSE mount / network FS / API-backed VFS, a single-dir listing can answer in single-digit ms while a recursive traversal is 100x slower than native — the proxy pays its per-op overhead once per ENTRY, so thousands of individually-fine round-trips dominate the macro number. If micro is fast, the finding lives in the serving daemon's per-entry CPU (path re-parsing, linear scans over an entry map), not the transport, and the control arm is the same traversal on the underlying filesystem.

- **A benchmark command that exits rc=1 with no output is a script bug, not a measurement — run the payload script BARE once before touching the harness.** hyperfine only reports 'terminated with non-zero exit code', so a missing auth header, a failing ws connect, or a MODULE_NOT_FOUND inside the wrapper all look identical. The bare run prints the real error (401, stack trace) and locates it in seconds; typical silent failures in API probes: the endpoint requires `Authorization` even on the init/read step, and a package resolvable only via `NODE_PATH` because the package manager's strict layout does not hoist it to the root.

- **A live tailing source stales the derived index UNDER the benchmark — rebuild immediately before measuring, and freeze the tailer for the window.** A product whose fast path requires a derived index (DuckDB file, cache) and falls back to the slow engine when the source outgrows it can flip mid-benchmark: the watcher appends rows between your rebuild and the hyperfine run, the index reads stale, and hyperfine reports `terminated with non-zero exit code 4` on the first warmup with no error text (the refusal is the measured command's stderr, which hyperfine swallows). That rc is the product's own fallback firing, not a perf result. Rebuild, verify the index artifact is newer than the source (`stat` both), pause the tailer for the measurement window, and note in the report that a user running the tailer live pays this staleness continuously — that is a UX observation, not a PERF row.

- **Measure cold AND warm on the live compose stack, and only restart it after proving nothing is in flight.** Order: 10 timed warm runs of the headline endpoint for the baseline; confirm zero active games/jobs/runs through the product's own status surface (or its store) so the restart kills no live work — say that check in the row; `docker restart <svc>`; poll the product's own /health until 200; then time the FIRST request (cold) and the immediate second (warm). On a persistent volume, cold==warm is itself evidence: nothing is cached, so the cost lives in per-request work (e.g. full-table GROUP BY aggregations) and there is no memoization to invalidate — quote cold and warm separately in the PERF row either way, and pair the wall numbers with in-store component timings (time the handler's own queries standalone against the store) to split 'many queries' from 'one slow query'. A restart that kills in-flight work is a finding about you, not the product.

- **Read the server's OWN access-log duration field before profiling a curl-inclusive number.** A hyperfine mean of 8.5ms over curl tells you the FORK cost; the server's per-request `duration=` log field (or X-Response-Time header) gives the server-side number (0.2-0.5ms) that separates 'the product is fast, the probe is slow' from a real latency. Quote BOTH in the report — curl-inclusive for the user-feel number, server-side for attribution — and profile only when the server-side number itself is high. Pair it with a boot-to-healthy poller (see shell-and-timing-pitfalls) for the cold figure; a boot that never exits cannot go through hyperfine at all.

- **Load the daemon through its OWN diagnostics surface before reaching for external load generators.** Daemons commonly expose an env-gated self-profiling endpoint (grep the source for the env-var gate, e.g. `PULSE_PPROF` + `/debug/pprof/profile?seconds=N`); hammering it with concurrent curls is a sanctioned real-use way to push self-CPU over a self-budget — the load IS an operator action against the product's own surface, no synthetic generator needed, and the gate's activation itself doubles as a docs check.

- **Verify the daemon's self-measured stats against an EXTERNAL observer (ps/proc) before trusting either.** A daemon that measures its own CPU from tick deltas between its own evaluations can report a confident 0.00% on beats that land inside a loaded window — the artifact is visible only by diffing its heartbeat series against `ps`/`top` over the same span. If they disagree, the reported field is the defect (file it), while smoothed decision inputs may still be behaving correctly — grade each separately.

- **Compute the contract's stated recovery/timing math BEFORE sizing a measurement window, then wait it out.** When a fix's contract is 'N clean evaluations at cadence C plus a smoothing constant T', first recovery appears only after ≥ N·C + T of quiet — sizing the quiet tail to that sum (plus margin) separates a false 'recovery did not happen' from an un-observed one. Verify recovery REACHES BASE, not just that it moves: a partial step proves the mechanism, reaching base proves the whole contract.

- **A suspiciously round latency (e.g. exactly 10.0s repeated) is a CLIENT TIMEOUT, not server work — find it in the backend log before filing a PERF row.** When the same endpoint returns the same wall time to the tenth of a second across runs, grep the server log for the matching request and read its `request:<Ns>` field: a number equal to the client's configured read timeout means the user is waiting for a doomed upstream call to time out (an external write that cannot succeed), not for real work. The row is then a defect row (timeout serialized into the user path — make the upstream call async/fail-soft), not a perf row, and re-time only after the upstream cause is fixed.

- **An -15 exit_code on a benchmark run is usually your own pkill/prepare script, not the target** — see the argv self-match rule in shell-and-timing-pitfalls before writing a PERF row from a killed run.
