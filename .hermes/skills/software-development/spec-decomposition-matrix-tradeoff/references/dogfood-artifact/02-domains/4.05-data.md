# Domain 4.5 — Data: inventory, meaning, lifecycle

Triage: 3×3×3=27; floor 5; status CASCADED; terminating ring 5.
Synonyms: observation=seen-state; change=event; delivery=attempt.

## Battery and cascade

### Ring 1 input set
- `data-q1-1` D `(file-observation,D,4.5)`: What fact is canonical? Answer: the last fully committed observation of a regular file at `(root_id, relative_path)`, not an inotify event and not an incomplete scan row.
- `data-q1-2` F `(scan-run,F,4.5)`: What does half-written data mean? Answer: rows in `scan_stage` tied to a non-COMMITTED scan are disposable and never appear in a digest.
- `data-q1-3` O `(event-retention,O,4.5)`: Who owns lifecycle? Answer: the service writes; the operator owns retention; v1 provisional default keeps current state indefinitely and delivered events/digests 90 days.
- `data-q1-4` C `(file-metadata,C,4.5)`: What grows at 10×? Answer: current rows scale with file count; events scale with churn; no measured target exists, so U-001 owns the capacity probe.
- `data-q1-5` A `(file-identity,A,4.5)`: Path, inode, or content hash? Answer: root id + normalized relative path is canonical; device/inode are diagnostics; content hashes are rejected because content need not be read.

Answers forced D-003, D-006, D-016, and D-019. Five classes produced ring 2.

### Ring 2 input set
- `data-q2-1` D `(change-event,D,4.5)`: What is a change? Answer: `DISCOVERED`, `METADATA_CHANGED`, or `DISAPPEARED` from the difference between two committed scans; rename is disappear+discover in v1.
- `data-q2-2` F `(file-observation,F,4.5)`: What if a file mutates while scanning? Answer: the scan records one stat sample; a later scan records the next state. It does not claim a coherent file-content snapshot.
- `data-q2-3` O `(root-config,O,4.5)`: How is a path attributable? Answer: immutable configured `root_id`; a root path move requires an explicit mapping, not silent creation of a new identity.
- `data-q2-4` C `(content-hash,C,4.5)`: Cost of stronger identity? Answer: hashing reads every byte each scan and changes the product into a content scanner; reject absent a content-integrity requirement.
- `data-q2-5` A `(rename,A,4.5)`: Could inode correlate rename? Answer: it can be a best-effort display hint only; inode reuse and cross-filesystem moves make it unsafe as truth.

New signatures: file-completion, timestamp-authority, deletion-semantics, privacy, schema-evolution.

### Ring 3 input set
- `data-q3-1` D `(timestamp,D,4.5)`: Which time is authoritative? Answer: service `observed_at_utc` for ordering; filesystem `mtime_ns` is payload and may move backward.
- `data-q3-2` F `(disappeared-file,F,4.5)`: Does disappearance mean deletion? Answer: no; it means absent from a completed scan and can also mean permissions/mount failure. A root-level scan failure suppresses disappearance events for that root.
- `data-q3-3` O `(schema-version,O,4.5)`: How does shape evolve? Answer: integer schema version plus additive migrations; old code must refuse a newer version.
- `data-q3-4` S `(relative-path,S,4.21)`: Can filenames leak? Answer: yes; no content is read, but root-relative names may be sensitive. D-019 adds configurable redaction and U-003 owns the destination policy.
- `data-q3-5` A `(file-completion,A,4.5)`: Wait for file stability? Answer: not for discovery truth; hourly digest coalescing reports the latest committed state in-window. A separate settle rule would hide legitimate append-only files.

New signatures: root-failure, digest-coalescing, event-provenance, retention-expiry, nullability.

### Ring 4 input set
- `data-q4-1` F `(root-failure,F,4.42)`: How distinguish empty root from unreadable root? Answer: a root scan has an explicit success marker; only successful scans may infer absence.
- `data-q4-2` D `(event-provenance,D,4.5)`: Can each event be proved? Answer: event links `scan_id`, previous observation id, new metadata, and service version.
- `data-q4-3` O `(retention-expiry,O,4.5)`: Can retention delete undelivered history? Answer: no; pending digest/events are exempt until delivery or explicit operator abandonment.
- `data-q4-4` C `(digest-coalescing,C,4.5)`: Keep every event or one line per path? Answer: keep every durable event; render one summary line per path plus counts, preserving audit without verbose posts.
- `data-q4-5` P `(nullability,P,4.5)`: What rejects malformed records? Answer: NOT NULL/CHECK/foreign-key constraints and migration tests; paths are stored as bytes-lossless OS strings serialized by Python's filesystem encoding rules, not assumed UTF-8.

All outputs resolve to existing decisions or owned unknown U-001/U-003. Candidate next signatures are aliases of ring 2–4.

## Required output — data dictionary

| Item | Type/shape | Meaning | Canonical/derived | Owner | Sensitivity | Retention |
|---|---|---|---|---|---|---|
| root | id, configured absolute path, policy | watched boundary | config canonical | operator | path may be sensitive | while configured + history reference |
| scan_run | id, root, start/end, status, error | one attempted reconciliation | canonical audit | service | low | 90d after success; failures 180d provisional |
| scan_stage | scan id + path + stat tuple | noncanonical candidate snapshot | staged/derived | service | filenames | until commit or startup cleanup |
| file_state | root+relative path, size, mtime_ns, mode, dev/inode | latest state from a completed scan | canonical current state | service | filenames/metadata | while present plus tombstone history |
| event | id, kind, old/new metadata, scan id, observed_at | committed state transition | canonical history | service | filenames/metadata | 90d after delivered; pending exempt |
| digest | stable id, UTC window, body/hash, status | bounded summary of committed events | derived but durable delivery unit | service | inherits event sensitivity | 90d after delivery |
| delivery_attempt | digest id, attempt, time, result class, receipt | proof of attempted posting | canonical audit | service | endpoint metadata, never secret | 90d |

Canonical-source rule: current file truth is `file_state` after a COMMITTED scan; historical truth is `event`; `digest` is a reproducible, durable rendering linked to event ids. Staging rows and notifications are never canonical.
