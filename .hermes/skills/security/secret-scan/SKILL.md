# Secret Scan

Daily Git repo secret scan → finding verification → Obsidian report → Dashboard update → user summary.

## Trigger

Running as a scheduled cron job; scanner output flags findings with repo path, file path, line content, and type (credential, openai_key, etc.). The scan covers all local git repos and optionally GitHub remotes (SCAN_SUMMARY line). **SCAN_VERSION 3 (scan #39): plaintext-hotspot scan — `references/plaintext-hotspot-dimension.md`**

Dashboard edit-points / `||` table rows / scan numbering: `references/dashboard-update-mechanics.md`.
A flat per-repo timeout is a SILENT coverage gap; repo-local git identity drifts; logs sit outside every PLAINTEXT_DIR: `references/scan102-flat-timeout-coverage-gap-2026-09-19.md`.

> 🕳️ **A CLEAN scan is not proof of a clean surface — read `references/clean-scan-blind-spots-2026-09-18.md` FIRST.** Scan #97 printed the clean path while **2 LIVE xKiro keys** sat committed in the DuckBrain `chat-archive` namespace store: four independent blind spots (hyphenated `sk-xt-` keys vs the `sk-` pattern, namespace repos at depth 3 outside the depth-3 walk, tz-less `--since` shrinking the window to ~19h, whole-line `is_false_positive()` swallowing a match in a 70 KB JSONL row). All four are fixed in `~/.hermes/scripts/scan-git-secrets.py` (11 patterns, 269 repos, true UTC window, ±120-char `fp_window()`); the reference lists the exact probe for each plus the liveness-probe and canary protocol to run before reporting CLEAN. **Scan #98 addendum → `references/scan98-evidence-liveness-and-window-laws.md`**: `/v1/models` is unauthenticated (use an authenticated probe; a UA-less probe 403s on every key), a known exposure ages out of the 24h window so clean ≠ fixed, exit 1 is the normal findings path, and resolve the report's status anchor BEFORE inserting a section.

> 📚 **Before deep-verifying a flag, check `references/known-false-positive-corpus.md`** — it documents recurring FP classes (off-by-one answer-corpus dummy keys, gitreins-poc GR-GAP-007 task prose, env-var NAME constants, test fixtures) with exact re-confirmation probes and the per-commit `-U0` pickaxe attribution command; a matching FP class re-confirms in seconds. (Scan History leading-pipe pitfall: rows start with `||` and fuzzy matching may accept a wrong-pipe-count anchor — verify pipe counts in the returned diff.)

## Workflow

### 1. Parse and Triage

Extract findings from the script output. Group by repo and file. Note the type (credential, openai_key, aws_key, etc.) and severity level (CRITICAL, HIGH, MEDIUM, INFO).

**Key principle: the scanner flags patterns, not secrets.** Every CRITICAL flag must be independently verified against the actual source file before being reported as a real finding.

### 2. Verify Every CRITICAL Flag

For each CRITICAL finding, read the actual file to confirm or refute it:

```bash
# Use search_files with context to see the lines around the match
search_files(path="/repo", pattern="<key-snippet>", context=3)
```

**PEM-key structural verification recipe (verified 2026-08-05 scan #1)**: to distinguish a synthetic test keypair from a real leaked key, run all four checks — (1) **decode the body**: extract the base64 between the header/footer and `base64.b64decode(body, validate=True)` + check first byte `0x30` (ASN.1 SEQ) — a valid decode only proves well-formedness, NOT liveness; (2) **grep upstream/repo-wide for the body prefix** (`grep -rl "<first ~20 chars>" <upstream-dir>`) — absence from upstream fixtures + presence only in test inputs = synthetic; (3) **read semantics**: variable name (`TEST_KEY_PEM`), companion cert (`TEST_CERT_PEM` in same file), usage sites (unit-test input dicts only), file path (`development/test_inputs/`, `_tests/`, `.speclang/assembled/`); (4) **check the commit story**: `git log --oneline -3 -- <file>` + commit timestamp vs scan window + whether the pattern appeared in prior daily reports (first appearance = verify from scratch; known = carry forward). A PEM whose body contains non-base64 text (spaces, repo names, literal `test`) is structurally impossible as a real key, full stop.

**When the current file is clean (key already removed from HEAD):**

The scanner flags a diff — the key may have been added and then removed in a subsequent commit. The current `read_file` will show a clean file, but the key IS in git history. Do NOT dismiss as false positive without checking history:

```bash
# 1. Find which commit introduced/removed the key (pickaxe search)
git log --all -p --full-history -S "<key-snippet>" -- <file>

# 2. Inspect the parent of the commit that removed it
git show <removal-commit>^:<file>

# 3. Check if the key existed in any prior commit
git log --all --oneline --diff-filter=A -- <file>
git show <creation-commit>^:<file>   # state before file existed
git show <creation-commit>:<file>    # state when file was first created
```

**When a finding is real:**
- Confirm the key format matches the claimed provider
- **Cross-repo key check**: If the finding is in a GitReins history file (`.gitreins/history/`), search ALL other repos for the same key snippet using `search_files`. The `GITREINS_LLM_API_KEY` env var propagates across every GitReins-enabled repo — if the key leaked in one, it's likely in all of them. Check repos listed in `gitreins propagate` targets or any repo with a `.gitreins/` directory.
- Check the key's exposure history: use `session_search` to find prior detections of the same key in other repos, or consult the Security Dashboard's **"Recent Critical Findings"** section which tracks key detections across all prior scans — often faster for well-documented keys. A key flagged 7 days ago in one repo and now appearing in another means it was never rotated — elevated urgency.
- Check if it's committed and pushed:
  - `git check-ignore <path>` — is the file/directory gitignored? If yes, the key is NOT in git history (local-only disk exposure). More reliable than manually checking `.gitignore` files, since nested or global gitignore rules may apply.
  - `git log --oneline -- <file>` — is the key in committed history?
  - `git remote -v` — are there remotes? If none, the repo is local-only and risk is lower
  - `git branch -r` — are there remote tracking branches?
  - `git merge-base --is-ancestor <commit> origin/<branch>` — definitive check: is the key-containing commit pushed to the remote? Returns exit 0 if the commit is an ancestor of the remote tracking branch (already pushed), exit 1 if unpushed.
  - `git log --oneline origin/<branch>..HEAD` — are there unpushed commits?
  - `git rev-list --count origin/<branch>..HEAD` — how many unpushed commits? High counts (50+) mean the key is buried in local-only history but may be hard to purge.
- Note whether it's a hardcoded literal or loaded from env
- For local-only repos without remotes: the key exists only on this machine — lower urgency but still rotate

## Pitfalls

- **Never trust the scanner blindly**: The scanner matches regex patterns. A variable reference `$SOME_KEY`, a fake key `sk-fake123`, and a real key `sk-or-v1-abc123` all match. Only source file verification distinguishes them.
- **Secret-store key-NAME constants are the FP, not the leak (verified 2026-09-17, scan #93)**: `RELAY_URL_SECRET = "cloud-relay-url"`, `CLOUD_CLI_OAUTH_TOKEN_SECRET = "cloud-cli-oauth-token"`, `GROK_AUTH_METHOD_CACHED_TOKEN = "cached_token"` (t3code `apps/server/src/cloud/*`, `provider/acp/GrokAcpSupport.ts`) all fired `credential/CRITICAL` — but the value is the identifier handed to the store (`secrets.get/set(<CONST>)`, `readSecretString(<CONST>)`), while the credential itself lives in the OS keychain. Five-second tell: grep the constant's usage for a get/set/read call; sibling consts on the same lines (`CLOUD_MINT_PUBLIC_KEY = "cloud-mint-ed25519-public-key"`, `GROK_AUTH_METHOD_API_KEY = "xai.api_key"`) and lowercase-dictionary values with no digits/uppercase confirm it. Scanner hardened 49→51 rules (scan #93). Full probe + rules: `references/known-false-positive-corpus.md` ("Scan #93").
- **A depth-1 clone makes the scanner report the ENTIRE upstream tree as "added" (verified 2026-09-17, scan #93)**: `/home/kara/t3code` is a fresh shallow clone of the public `pingdotgg/t3code`; its boundary commit (`.git/shallow`, = `origin/main` tip) has no parent, so `git log -p` emits all **21,925 files / 4,254,638 lines** as added and every identifier-shaped constant in published upstream code looks like a new in-window finding. Detect in seconds: `git rev-list --parents -1 <sha>` returns a bare hash (no parents) while `git rev-parse origin/main` equals it. Then separate real local work — `git log --since=<cutoff> --oneline`, and `git branch -r --contains <sha>` / `git ls-remote --heads origin` to prove a branch was never pushed (a branch with no upstream that is absent from the remote = nothing published). Sweep the boundary tree with your OWN patterns anyway: #93's sweep of 4.25M lines found 4 value-shaped hits, all FP inside a vendored upstream test tree, and 88 `-----BEGIN` marker lines with 0 base64 bodies.
- **GitReins echoes live API keys into committed history files**: GitReins' evaluation pipeline captures environment variables (specifically `GITREINS_LLM_API_KEY`) and writes them verbatim into `summary.md` and `verdict.json` files under `.gitreins/history/`. If these files are committed to git, they contain the actual live API key — same severity as a hardcoded credential in source. The `.gitignore` fix (`echo '.gitreins/history/' >> .gitignore`) prevents future leaks but does not purge existing keys from git history. After detection: (1) check if `.gitignore` already excludes `.gitreins/history/`, (2) verify with `git show <commit>:.gitreins/history/<date>/<run>/summary.md`, (3) cross-reference the key with findings from other GitReins-enabled repos (the same env var propagates everywhere), (4) if real: rotate key, rewrite git history, and verify no other repos have the same exposure.
- **Scanner output may attribute secrets to the wrong file**: When the scanner shows `+++ b/filename` lines, it's reporting from a git diff — the current working tree may differ from what was committed. The scanner can flag a file that was already fixed (e.g., `consensus.yaml` showed `+++ b/consensus.yaml` with a real key, but the current file correctly used `${DEEPSEEK_API_KEY}`). The actual hardcoded key lived in test source files. Always `read_file` the flagged file — do not rely on the scanner's file attribution.
- **Clean current file does not mean clean repo**: The scanner flags diffs. If the key was added in one commit and removed in a subsequent commit, `read_file` will show a clean file — but the key IS in git history. A clean `read_file` is NOT sufficient to dismiss a finding as false positive. Before calling FP, verify with pickaxe search (`git log -S "key"`) and inspect parent commits (`git show <commit>^:file`). The key is real if ANY commit in the history contains it, not just HEAD.
- **Go test env-var fallback is a real secret, not a FP**: Pattern: `if apiKey := os.Getenv("X"); apiKey == "" { apiKey = "sk-real" }`. The env var check is present, but the hardcoded fallback IS a real key. Do not dismiss this as "uses env var" — the fallback value is what matters. Distinguish from true FPs like `sk-test-fallback` (contains "test"/"fallback" — synthetic).
- **Documentation files are the #1 FP source**: `.memory-bank/findings/` files, `docs/`, and tutorial files intentionally contain example keys. Exclude these paths from the scanner.
- **Diff-window re-flagging ≠ new finding**: a diff-scanning scanner re-flags a known line whenever ANY commit touches its file — even a gofmt alignment reformat. The hermes-canopy dev JWT vanished from Jul 27–29 diffs and re-appeared Jul 31 purely because GAP-001/002 commits reformatted `config.go` (value untouched since Jul 24). Before treating a reappearing finding as new: `git log -S '<value>' -- <file>` (pickaxe) + check the dashboard's prior bullets for the same value. Same value in history = same finding, just back in the diff window.
- **Rebase rewrites committer dates — old commits re-enter the 24h diff window (verified 2026-08-13 scan #3)**: a file whose last commit is WEEKS old can re-flag when its repo is mid-rebase. The scanner's `git log --since=<cutoff>` filters on COMMITTER date (not author date), and a rebase rewrites committer dates to now while preserving author dates — so every rebased commit re-enters the window at once. Diagnostic trio when a finding's file looks stale: (1) `git log -1 --format='%h | author %ad | committer %cd' --date=iso` — author date old + committer date today = the tell; (2) `git branch -a` — `* (no branch, rebasing main)` (detached HEAD) confirms; (3) `stat -c '%y' <file>` matches the committer-date rewrite (checkout during rebase). Verdict: benign window artifact — content unchanged (grep the flagged value), NOT a new secret; expect the same line to re-flag on EVERY scan until the rebase completes or is aborted. Distinct from the tz-shift artifact (cutoff-computation issue) and from new-commit re-flags (file actually touched): here NO commit touched the file in the window, the rebase alone re-exposed it. Optional recommendation in the report: complete/abort the stalled rebase to stop the repeated re-flags. Instance: gitreins-poc `specs/04-Guard-System.md:276` `AKIAIOSFODNN7EXAMPLE` (guard-system detection-regex table, content unchanged since `5f05781` Jul 19) — see `references/known-false-positives.md#gitreins-poc-specs04-guard-systemmd-aws-example-key`.
- **Scanner exit codes (fixed 2026-09-19)**: `sys.exit(1)` fired on ANY finding, so INFO-only days (repo timeouts) reached the cron wrapper as "Script Error". Now nonzero ONLY for CRITICAL/HIGH; INFO-only exits 0. Nonzero = real severity to verify, never a crash.
- **Large-repo timeouts are a coverage gap — close it in the same run**: hermes-observatory (5.8G) and duckbrain/namespaces/scheduler (2.3G) exceed the 30s per-repo default. Import the scanner as a module, set `m.REPO_TIMEOUT_S=300`, re-run `m.scan_repo(repo, since)` per timed-out repo and report the rescan verdict (2026-09-19: both CLEAN at 300s).
- **Multi-scan days**: When a scan already ran today, append to the existing file rather than overwriting. Cross-reference earlier findings (same hits = repeatable, different hits = investigate).
- **`insert-daily-scan-section.py` leaves no blank line before `## Full Day Summary` (cosmetic — expected, verified 2026-08-03 scan #2)**: the script inserts the new section at the heading's offset, so the section's final `## Status` block ends immediately followed by `## Full Day Summary` (the pre-heading blank line ends up BEFORE the inserted section instead of between them). Markdown renders the ATX heading fine and `verify-dashboard-patches.py` check #5 still passes. This is script behavior, NOT corruption — do not "repair" it with a follow-up patch (a repair write on the Flatpak path risks the file-lock timeout for zero benefit). If the gap ever needs closing, fix the script's `content = content[:idx] + section + content[idx:]` line, don't hand-patch the daily file.
- **Hand-patching Obsidian files with the patch tool — verified failure modes & recoveries (2026-08-03 scan #3)**: the scripted paths (`cat >>` for appends, `scripts/insert-daily-scan-section.py` for insert-before-summary, Python one-pass scripts for the dashboard) exist because the patch tool's fuzzy matcher chokes on these files. When hand-patching anyway, expect and recover from: (a) **V4A multi-hunk patch on the daily file fails validation** with `hunk (no hint) not found — Found 2 matches for old_string` when the anchor line is near-identical to another line (scan #1 vs scan #2 status blocks differ only in the tail: "Both flags are the same benign constant line in hivemind-work" vs "Same benign constant line as scan #1"). Recovery: re-read the exact region and use the **remove+add form with the FULL exact line** as the anchor — context-only hunks fuzzy-match ambiguously, exact `-`/`+` lines don't. (b) **V4A also fails on the dashboard's `_Last updated:` line even though grep confirms it's unique** (1 occurrence) — the fuzzy matcher still reports "Found 2 matches". Recovery: switch to replace mode with a **multi-line anchor spanning the line end + the following blank line + start of the next bullet** (e.g. `yt-dlp Day 40)_\n\n- 🟡 **2026-08-03 15:35 UTC:**`). (c) **Replace-mode old_string must reproduce blank lines exactly** — omitting the `\n\n` between paragraphs yields `Could not find a match for old_string`; include it. (d) **Scan History rows have variable leading pipe counts** (`|`, `||`, `|||` — the table is messy) — before building a row old_string, `search_files` for the exact row by timestamp instead of trusting a truncated read_file (the 100K read budget cut the table mid-row; guessing 4 pipes when the row had 3 produced a false "Found 2 matches" via fuzzy matching). Rule: for ANY patch on these files, grep/read the exact target text immediately before patching — never reconstruct it from memory or a truncated view.

- **Cross-day scan protocol — appending to the previous date's file**: When a scan runs past UTC midnight and the next calendar day's `YYYY-MM-DD.md` file doesn't exist yet in `Secret Scans/`, append to the previous day's file. Follow the same logic as the CVE briefing skill's cross-day protocol:

  **Pre-check for BOTH date files**: Search for BOTH today's and tomorrow's `YYYY-MM-DD.md` files near UTC midnight:
  ```bash
  search_files(pattern="2026-07-1*", target="files", path=".../Security/Secret Scans/")
  ```
  If the next day's file already exists (created by a concurrent cron job), read its tail to determine the next scan number. If it doesn't exist, use the previous day's file.

  **Determine scan number**: Read the tail of whichever file has the highest scan number. Scan numbers are global across date-file boundaries — a scan that appends to the old date file picks up the sequence from the last scan in that file, and the first scan that creates the new date file notes: `**Scan #**: N (first scan written to this date file; Scans #N-2–#N-1 were appended to YYYY-MM-DD.md)`.

  **First scan of a new date file with N > 1 needs a numbered `## Scan #N` section heading (verified 2026-08-14 scan #6)**: when the first scan written to a new date file continues global numbering (scans #1–#5 appended to the previous date file → the new file's first scan is #6), include a literal `## Scan #6 — HH:MM UTC (HH:MM CT)` section heading IN ADDITION to the top metadata block — `verify-dashboard-patches.py` check #5 greps for `## Scan #{N}` whenever `--scan-number > 1` and FAILS without it. The unnumbered top-section format (title + metadata + Results + Status + Full Day Summary) is only sufficient when the new file's first scan is scan #1. Also repeat the "first scan written to this date file; scans #1–#N-1 appended to YYYY-MM-DD.md" note inside that section, and pass `--date <new-date-file>` (not the previous file's date) to the verify script since the dashboard row/bullet carry the new date.

  **Same-day off-slot fires are NOT cross-day (verified 2026-08-14 scan #6, fired 10:00Z between the 05/11/17/23Z slots)**: an off-slot fire that stays within the same UTC day creates the new date file normally with SCAN_TIME-authoritative labeling — no cross-day protocol, no append-to-previous-file. The schedule grep (`grep -n '"name"' ~/.hermes/cron/jobs.json` → `expr: 0 5,11,17,23 * * *`) is only needed to rule out a date-boundary case; the 04:00Z variant above is the cross-day case, a mid-day off-slot fire is not.

  **Note in the report**: When appending to the previous day's file, add a note in the Status section: `**Note**: This scan (#N) ran on Jul 14 UTC / early Jul 14 CT. It's appended to the YYYY-MM-DD file per multi-scan cross-day protocol since the YYYY-MM-DD.md file doesn't exist yet.`

  **04:00Z variant — scan BEFORE the 05:00Z first slot (verified 2026-08-14, scan #5)**: the normal slots are 05/11/17/23Z, but a scan can fire at 04:00Z (= 23:00 CT of the PREVIOUS day). The previous day's file then already holds scans #1–#4 and the new UTC day's file doesn't exist → append as the previous file's next scan (#5). Adjust the note language from the template: the scan ran `Aug 14 04:00 UTC / Aug 13 23:00 CT` — LATE previous-day CT, NOT "early next-day CT" as the template example implies. Dashboard bullet + Scan History row are dated with the APPENDED-TO date (`2026-08-13 04:00 UTC`), not the scan's UTC date (`2026-08-14`). If a fire time looks off-slot, confirm the schedule convention via `grep -n '"name"' ~/.hermes/cron/jobs.json` (the Git Secret Scanner block shows `schedule.expr` `0 5,11,17,23 * * *`, `last_run_at`, `next_run_at`) — but SCAN_TIME in the scan-script output is authoritative for labeling. **Dashboard artifact labeling that keeps the verify script green (verified 2026-09-17, scan #92)**: label the three dashboard artifacts by the APPENDED-TO CT day with the true instant in both zones (`2026-09-16 23:01 CT (04:01Z 09-17)`) and run `verify-dashboard-patches.py --date <appended-to-date> --scan-time "23:01 CT" --scan-number N` → all five checks green; the true-UTC-first form (`2026-09-17 04:01 UTC (23:01 CT 09-16)`, scan #87 style) makes checks #1–#3 fail on the date prefix, and passing the scan's own UTC date fails #5 (that day's file does not exist yet). Details + the table-form Full Day Summary insertion recipe: `references/dashboard-update-mechanics.md`.

  **Verification script — cross-day is FIXABLE with `--date` (verified 2026-08-14, scan #5)**: `verify-dashboard-patches.py` takes `--date YYYY-MM-DD` (default: host-local `date.today()`). For a cross-day append, pass `--date <appended-to-date>` alongside `--scan-time`/`--scan-number` (e.g. `--date 2026-08-13 --scan-time "04:00 UTC" --scan-number 5`) and ALL checks go green — no expected-FAIL to skip. The dashboard row and bullet MUST also carry the appended-to date (`|| 2026-08-13 04:00 UTC | ...`), because checks #1/#3 match rows and bullets on `args.date`. The older documented behavior ("script reports `❌ FAIL: Daily report ... does not exist` — skip the check failure; the data is correct") only bites when `--date` is omitted AND the host date disagrees with the appended-to date — always pass `--date` explicitly on cross-day appends. The script also searches for `--scan-time` string exactly in the Scan History row — the row MUST contain the literal `UTC` suffix and match the established git-secrets row convention: `|| YYYY-MM-DD HH:MM UTC | N (M active) | <findings> | <real> | <status> |`. **Fix-forward, don't tolerate the failure (verified 2026-08-03)**: a row inserted as `|| 2026-08-03 05:00 | ...` (no `UTC`, wrong column style) failed check #3; reformatting to the convention (`|| 2026-08-03 05:00 UTC | 92 (45 active) | 2 (both FP: ...) | 0 | 🟢 Clean — Scan #1. ... |`) passed cleanly. To replace a misformatted row wholesale: `sed -i '/<unique-anchor>/c\|| <correct row>'` — the `c\` change-line command replaces the entire line with no pipe-escaping issues (contrast the `a\\`/`i\\` insert pitfalls). Only if you deviate from convention is manual verification needed.
