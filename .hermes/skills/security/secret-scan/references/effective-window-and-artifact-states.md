# Effective window & the three clean-scan states (moved verbatim from SKILL.md, scan #102)

Scanner v2 reads `git log --since=` with a tz-less ISO of a UTC cutoff, so its window is
effectively ~19h on this UTC-5 host. Read this before calling a 0-finding scan "clean".

---

**0-finding scan ≠ content change — check the scanner's effective window (verified 2026-08-04 scan #3)**: `scan-git-secrets.py` line 194 emits `since_iso = cutoff.strftime('%Y-%m-%dT%H:%M:%S')` — a timezone-less ISO of a UTC cutoff. `git log --since=` interprets tz-less ISO as LOCAL time (host is UTC-5), so the effective cutoff shifts +5h: a 17:00Z scan's real cutoff is 22:00Z (effective window ~19h, not 24h). Consequence: commits in the 17:00–22:00Z band drop out of the window one scan earlier than advertised. When a scan suddenly reports 0 findings while prior scans flagged known content, do NOT assume the FPs "rolled out" — verify: `git -C <repo> log --since=<tz-less ISO> --oneline -n 1 -- <file>` (0 hits) vs the same query with `+00:00` suffix (1 hit = the commit is in TRUE UTC window but outside the effective one). Repro-proof pattern for the report; the FP corpus stays in the working tree and will re-flag on new commits. **Two-phase roll-out (verified 2026-08-04 scan #4 23:01Z)**: (a) ARTIFACT phase — 0 findings while the `+00:00`-suffixed query still returns the FP-source commit (content in TRUE window but outside the effective one); report as window artifact. (b) GENUINE phase — BOTH queries return 0 hits (FP-source commit older than the true 24h cutoff): the FPs have genuinely rolled out and the clean result is real — say so explicitly in the report (`git log --since=<cutoff with +00:00> --oneline -n 1 -- <file>` → 0 commits, plus working-tree grep of the stable key values unchanged), and note the corpus will only re-flag if those files receive new commits. **Same-day clean carry (verified 2026-08-12 scan #2)**: once scan #1 of the day has confirmed GENUINE roll-out (both queries 0 hits), a later same-day scan that again reports 0 findings needs ZERO re-verification — the FP corpus cannot re-enter any later effective window (each scan's cutoff advances with T), so no git probes are required. Report language: "consistent with scan #1's verified genuine roll-out; steady state; corpus re-flags only on new commits" (2026-08-12 scan #2: full insert-daily-scan-section.py + one-pass A+B+C dashboard cycle ran first-try with zero git repro, verify script all green). **The ARTIFACT phase lasts exactly ONE scan — never predict a next-scan re-flag (verified 2026-08-11 scan #4)**: a commit in the artifact band (T−24h, T−19h] — inside the TRUE window, outside the effective one — can never re-enter any later scan's effective window, because each scan's effective cutoff (T−19h) advances with T, so C ≤ T−19h < T′−19h for every later scan T′. The next scan therefore always confirms GENUINE roll-out (both queries → 0 hits); the FP re-flags only via a NEW commit to the file, never via the aged-out commit itself. Day-boundary case (23:00Z scan #4): `bd89b84` (gitreins-poc board Tick 166, 23:28Z Aug 10) was in the true window (cutoff 23:00:03Z Aug 10) but out of the effective cutoff (04:00Z Aug 11); the next day's 05:01Z scan has true cutoff 05:01Z Aug 11 > commit → genuinely rolled out. The scan-#4 report's prediction "will re-flag on tomorrow's scan #1" was WRONG — correct report language for an artifact at the day's last scan: "single-scan artifact; genuine roll-out confirmed at the next scan; corpus re-flags only on new commits to the file". Scan #4 sequence: totalstack `89fe55ad6` (20:22Z Aug 3) and off-by-one `24e6975` (19:29Z Aug 3) both outside the true cutoff 23:01Z Aug 3 — the day progressed artifact (scan #3) → genuine (scan #4), and report language should track that distinction so the audit trail doesn't keep calling a real clean scan an artifact. Optional fix: append `+00:00` to `since_iso` for a true 24h UTC window.
