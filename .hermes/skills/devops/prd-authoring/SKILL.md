# PRD / spec authoring

For requests like "write me a PRD", "give me specs for X", "a prd for each of these" — the output is a document the user reads on a phone and that foremen later execute from. Format/legibility expectations below are the user's, not defaults.

## Procedure
1. **Ground it first.** Collect live evidence before writing a word: repo paths and remotes, board row counts, scheduler lane state, the log lines the claim rests on. Every number must trace to something checkable. Never invent a metric; if you only have an anecdote, label it as one.
2. **Write the markdown** in this order: one-liner (what it is, one sentence) → measured problem with a NAMED case file from our own history (real numbers + what the incident cost) → value case (the asymmetry: run-once vs saved-per-use, fleet scale) → user stories (3-5, "As a <role>, I <do>, I get <result>") → **acceptance criteria (AC-n, see the section below — one per story minimum)** → design depth (schema, interface, design rules as imperatives) → scope in/out → **success criteria as replayable proofs against real history** ("replay incident X: the check fires / the query returns the signature"), never "improves quality" → cost & shape (effort S/M/L, dependencies, repo home) → risks with mitigations → why-others-want-it.

## Acceptance criteria — mandatory in every PRD, and transferable

Every PRD carries a numbered **`AC-n`** block **before** its success criteria. Two different jobs: success criteria prove the DOCUMENT was worth building (incident replays, adoption); acceptance criteria are what a worker or judge EXECUTES, one row each, with no interpretation left.

- **Form:** `AC-n: Given <state>, when <action>, then <observable result> — proof: <command / test / artifact / number>. (T|C|M)` where T = automated test, C = command or probe with its expected output, M = manual artifact that must exist.
- **Coverage:** at least one AC per user story; in requirements-numbered documents (R1..Rn), every requirement maps to >=1 AC. A requirement with no AC is unscoped work.
- **Banned:** "works correctly", "is robust", "improves quality", "handles edge cases properly". If you cannot name the command or the number, it is not a criterion.
- **Anti-gaming:** at least one AC per PRD that a green-but-did-nothing implementation cannot pass (regression replay, byte-diff, a counter only the real path increments). An acceptance test that cannot fail is a lie.
- **Transfer verbatim.** The AC list is what goes into the board row's `acceptance_criteria` field (the fleet's existing convention — hundreds of live rows carry it) and into the worker brief. Never paraphrase it on the way in: the whole point is that PRD → row → worker needs no retranslation.
- **Blocked is a state, not a deletion.** An AC that cannot be run yet keeps its row and gains `BLOCKED-ON: <thing>`, which you file as a dependency.
- **Design rules get ACs too.** Where the design says "never X by construction", the AC is the test that proves the impossibility (constant-surface test, no-state-reuse test, capability-error test). A rule with no test is one refactor from silent disappearance.
3. **Bake honesty rules into the design**, not just the prose: reporting tools carry provenance labels (absent data renders "not captured", never 0); "verified"/"proven" fields may only be populated by an actual run; ambiguous answers are surfaced, never silently narrowed.
4. **Deliver both formats** next to each other, same basename: `.md` (source of truth) and a self-contained dark-theme phone HTML via `scripts/md2html.py`. No external CSS/fonts/images. **Verify the render every time** — run the corruption check in `references/delivery-and-filing.md` before reporting, because a broken HTML still reads as a document and the user will find it before you do.
5. **File it the same turn**: board row on the OWNING project's board (shape per repo — see references), a spec row in that project's memory namespace, and a pointer to the PRD path. Status lives in the doc header AND the board row: `proposed` by default, `deferred` when told deferred, `approved` when approved.
6. **Report short**: one line per PRD on what it is plus the case file it rests on, then MEDIA: lines for the HTML attachments. Never paste the docs into chat.

## Frame it around the ask, not around your analysis

The user asks a question; the document is the answer to it. Two failure shapes, both of which earn an immediate "rewrite it, something is not right":

- **Leading with the design analysis and burying the asked-for artifact.** When the question is "what's that list look like", the list is a top-level section near the top — not a table inside the scope section. Order the document so its first sections answer THEIR question, and let the design reasoning follow.
- **Organising the doc as a rebuttal.** Correcting the user's proposal is normal and expected, but the correction belongs in the design rules as a stated decision with its measured basis. Never structure it as a section titled after their rule followed by why they are wrong — a document shaped like an argument reads as one, and the user is being sold to rather than informed.

When a review comes back with "this is not right", check these two before touching prose: what did they ask for, and is it the first thing the document delivers?

## Depth: what "in-depth" means to this user
The failure mode to avoid is the **narrow PRD**: a document that specifies the detection mechanism and stops. Read-back from the user when that happens: "it feels really narrow — I can see how it handles some diff stuff but I don't see the full feedback loop." Detection is one step of a system; spec the whole circuit.

For any tool that watches, guards, or reports, the design section MUST carry all of:
1. **State model first** — the two or three states whose *edges* are the problem (e.g. declared / on-disk / in-process for config; wanted / actual / proven otherwise). Name which edge each incident actually lived on. A differ that reads one state and calls it truth is the narrow shape.
2. **Taxonomy** — enumerate the classes of the thing (drift, failure, violation) with one real example each; a single "it changed" class means the doc is unfinished.
3. **The loops, each with its closure** — trigger → classify → act → **verify** → learn. Every loop must state what makes an item CLOSED (and what re-escalates it), what it feeds next, and how it compounds instead of nagging (recurrence → guard/pin/runbook; precision floor → demote the class). A loop without a closure rule is the gap the user is asking about.
4. **Boundaries section** — what the tool explicitly is NOT and never does (no authorship, no management, no storage). Boundaries read as engineering maturity here, not hedging.
5. **Per-adapter/per-source scope table** — what each input can and cannot answer, including visible "unmonitored" states rather than silent absence.

For any spec that defines an **interface or tool surface**, the design section must additionally carry:

6. **Parameters, never verb names.** A table of verb names reads as complete and is not. For every verb give its arguments, its return shape, and what backs it — and derive that by reading the REAL surfaces on both sides rather than from memory: make each tool document itself (a self-describing CLI, e.g. `toolsd describe --json` / `toolsd help <verb>`, beats any list you recall) and enumerate the counterpart surface the same way before claiming parity. State the divergences you find explicitly, because they are where the implementation breaks: a whole-file read primitive cannot serve an offset/limit windowed read; a diff-only patch primitive cannot serve an `old_string`/`new_string` patch. A surface spec without parameters gets rejected on exactly this point.
7. **The cardinality rule, stated as a hard constraint.** If the design fans out across N instances (N bunkers, repos, agents, endpoints), say whether the surface grows with N. It must not: **the tool count is fixed by the number of verbs, and the target is an ARGUMENT** resolved explicit-argument → session binding → refusal (never a global default). A per-instance design means N × M registrations and a tool list that mutates every time an instance spawns or dies. Name the wrong turn being closed and show the arithmetic (`20 bunkers × 10 verbs = 200 registrations`).
8. **Capability variance is an ERROR, not a dynamic surface.** Instances differ — older build, missing dependency, stopped. The rule is that the verb STAYS on the surface and the call returns a structured `capability_unavailable` naming what is absent. A silently missing tool is strictly worse, because the caller cannot distinguish "not supported" from "not loaded" from "forgotten".

9. **Session-scoped mutability is a SEPARATE axis from instance cardinality — specify both, or the spec is wrong in one direction.** Item 7 constrains the CATALOG (the verb set must not grow with the number of instances). It says nothing about which verbs *a given session* may enable, and conflating the two produces one of two wrong documents: a frozen surface that forbids per-session enable/disable, or a fanned-out one. State it as its own rule: **the enabled set is per-session and mutable — a session can enable or disable a verb mid-life, and that changes only the list THAT session is offered.** One constant catalog; N independently mutable session views.

   The measured failure this prevents: a persistent toggle that writes ONE global config file read by every session. Enabling a verb for one session then silently changes what every other session is offered — the same shared-mutable-pointer shape as an ambient "current target" global. **A session's enabled set is session state, never global config.** Confirm where the existing toggle actually writes before designing around it (a per-run flag is usually genuinely per-session but ephemeral and start-time-only; the persistent surface is usually the global one).

   Then split tool STATE by layer, because "never reuse another session's state" has an obvious over-correction that costs memory × sessions for zero isolation gain:
   | Layer | Sharing |
   |---|---|
   | Registration metadata (name, JSON schema, description) | **shared, immutable** — identical for every session |
   | Enabled set (which verbs this session sees) | **per session**, mutable — the isolation boundary |
   | Execution state (client connection, plugin instance, session-scoped caches, open handles) | **per session, never pooled** — this is where reuse actually leaks |

   A pooled stateful client handed from session A to session B leaks A's subscriptions, working directory, half-open files, cached reads and document state. Envelope those per session; pool only what is provably stateless. State the cost honestly: per-session state scales with CONCURRENTLY ACTIVE sessions, not total session starts, so the fix for an expensive client is to make it stateless or lazy — never to share it.

   Specify the mechanism explicitly: `constant catalog → this session's enabled row → per-session projection into the prompt → dispatch against THIS session's own set → instances keyed (session_id, tool), released at session end`. Make the refusal for a DISABLED verb distinct from the refusal for an UNSUPPORTED one (`tool_not_enabled_in_session` vs `capability_unavailable`) — one means "you turned this off", the other "this cannot work here", and collapsing them makes a deliberate choice read as a broken dependency.

Each of 6–9 needs its own replayable proof: a **constant-surface** test (spawn one instance and destroy another, then show the offered tool list is byte-identical), a **parameter-parity** test (same arguments local vs remote, diff the output), a **capability-error** test (call a verb the target genuinely lacks; the verb is still present and the error names the missing piece), and for item 9 a **session-isolation** test (two concurrent sessions toggle different verbs in the same minute; each offered list matches only its own choices and the GLOBAL config is asserted byte-identical before and after), a **no-state-reuse** test (A leaves a distinguishable artifact in a warm stateful tool; B loads the same tool and must not contain it) and a **no-stranding** test (kill a session holding state; its instances are reclaimed, not leaked into the next session's footprint).

**Objection-driven sections.** When the user raises a specific doubt about a design, answer it as its own named top-level section ("the critique, taken seriously") that states the objection, names the failure modes behind it, and gives the design rule that kills each. Four of these recur:

- *"It feels like a pipe dream to get everyone (else) aligned"* → **Adoption realism.** Name the two ways it becomes a pipe dream and kill each with a rule: (a) requiring every existing thing to migrate to your format → the tool adapts to their formats, never the reverse; (b) the tool becoming the single point of failure for the work it watches → fail-open, the wrapper runs the job/task itself and a recording failure never blocks it, and the read-only mode has no runtime dependency at all. Then give three progressive modes with per-item opt-in (observe with zero changes → reversible wrap, with a documented byte-identical unwrap → own/declare), and a **measured inventory of the surfaces** (count them live on the target box) so the adapter set is finite and named instead of hand-waved. Where declaring expectations would be the adoption blocker, make the tool learn a baseline and alert on deviation instead — declarations become an optional upgrade.
- *"How are we actually going to use this data to improve things?"* → **Value = decisions.** Reorganize the doc backwards from the decision, not the data: a table of loops with data → decision → who decides → cadence → the metric that must move. State a sunset rule (a score that drives no decision in a quarter is retired, loudly). Add a structural anti-gaming paragraph — what a metric-optimizing actor would do, and the mechanism that makes it impossible (receipts require real artifacts/tests; scores come from store-side joins, never self-reports) — plus the honest trap by name (measurement culture: dashboards, no behaviour change, real cost).
- *A tool that would touch sensitive material (credentials, keys)* → **Boundary + threat model.** A "never does" table (stores/reads/copies nothing sensitive), a compromise table (losing each component → what the attacker gains → blast radius) that shows the design is a smaller prize than the status quo, custody tiers where the tool is identical at every tier (the upgrade path is adopting an existing manager, never building one), and the operations choreography that keeps plaintext out of the tool entirely (human issues → register only a reference → inject via the manager's own CLI → probe with the new value → flip with an overlap window → rewire consumers and require their checks → verify end-to-end → retire the old value; abort anywhere leaves the previous reference active).
- *The user points at a sibling project with overlapping concepts* → **Division of labour.** A table of the one question each answers, its altitude, and its blind spot; an explicit "reuse now (free)" list (lifecycle model, storage schema, classification tiering, any query surface worth adopting rather than rebuilding); and the rule that a revival decision is a SEPARATE decision point — never two collectors for the same stream.
- *"How do we get this into our existing loops?"* → **Integration points, cost-ranked.** Name the loops that ALREADY exist in the org (tick/dispatch, QA, dogfood, commit gate, incident close, scheduled jobs) and give the hook into each as its own board row. Order them by process-change cost and say which is which: purely additive hooks (consult at dispatch, feed from existing structured findings, append a suggestion to an existing failure output) versus the one that needs a new convention (a required decision at close — absorb-or-acknowledge). State plainly which single hook decides adoption, and design the additive ones to prove value before the mandatory one is asked for. Carry the artifact-ownership decision too — where the knowledge lives, and that updates travel with the code and pass human review.

**Audit the platform before designing the build.** When the design needs capabilities from a system you do not control (the agent framework, a runtime, a daemon), MEASURE what it already does before specifying what must be built. The user will ask for this explicitly in the form "first make sure this is all correctly supported in <system>, and then figure out how we build it" — treat it as a gate, not a preamble. The order is: enumerate every capability the design requires → probe the live system for each one → record a support table → and only then write the build list. It resizes the work and routinely corrects your own assumptions.

Table columns that make it worth reading: **capability · state (already true / partial / missing) · the evidence (a command output, a config line, a process list) · what it means for the design.** Two outcomes to expect, and both change the plan:

- **Requirements already satisfied.** A claim that a subsystem must be rebuilt is often wrong. Check whether the isolation or guarantee you were about to design already exists structurally — then check whether anything TESTS it, because behaviour that is real but untested is one refactor from silently disappearing. The actionable row becomes the pinning test, not the feature.
- **An available interim.** An existing extension point (a hook, a gate, a wrapper) can enforce the rule before the native path lands. Name it as the interim so the work starts earlier.

Close with the resized scope in one line — "N of M requirements already ship; the build is one gap plus a test" — so the reader sees the corrected job size rather than your original guess. Record the audit as its own board row when it contains a finding (a gap plus its pinning test), not only as prose in the doc.

**Prove the mechanism live before publishing.** When the design rests on an OS/platform mechanism, run a throwaway probe on the target box and fold the MEASURED numbers into the doc — including whatever contradicts the design. One probe on this class of doc caught a false-positive source (an anonymous-memory object reporting an absurd apparent size) that became a shipped filter rule, and produced three live cases of the very condition the tool detects. Evidence turns a proposal into a plan and finds design bugs while they are cheap.

**User-supplied mechanisms are design authority.** When the user proposes how it should work ("compare the open file descriptors and inodes against what's on disk"), give it a named section in the PRD, spec it properly, and record it as a decision row — then state plainly which parts his mechanism covers and which need a companion rule. Do not bury it in prose and do not silently substitute your own approach.

**An alternative DELIVERY PATH he proposes is the same class of contribution, and the correct response to one you previously ruled out is to re-examine the ruling, not defend it.** Separate the objection's parts and test each against the mechanism's actual failure mode: one part is usually true but irrelevant to the job the path serves, and only becomes decisive when the path is used outside that job. The shape to look for: "a network filesystem pays a round trip per metadata operation" is true, and only bites if builds traverse it — so keep builds off that path and the objection dissolves. When you do reverse a scope call, leave the superseded reasoning visible as a marked note stating why it was wrong, so the exclusion is not re-litigated by the next reader.

When two paths survive, do not pick one — **split them by strength and publish the comparison**, one row per property (how an edit lands, how a build runs, transport, tool fidelity, latency, credentials, failure mode, isolation). Name the single rule that makes the weaker path safe, and then the limitations that rule does NOT cover, as design requirements rather than discoveries: a mount gives file-level edits and never execution, but it also cannot enforce per-session binding, so its concurrent-write guard has to be the lease registry. Prefer the path that needs the least new equivalence work — a real filesystem makes the existing tools correct by construction instead of by careful parameter matching, which is worth stating as the reason to keep it.

## Task-only requests (one feature, not a PRD)

"A task for <project>: make sure it <does X>" is NOT a PRD request — the deliverable is the board row alone. Do not manufacture a .md/HTML pair to look thorough; a single mechanical feature gets one row on the owning project's board, and the row is the spec of record.

- **Recon before writing a word — the row's `reasoning` carries measured numbers, never adjectives.** Count the coupling and give a per-package breakdown ("87 direct `time.Now()` sites: scheduler 53, dashboard 14, … plus 22 `Since`, 9 `Sleep`"), and name the live casualties that make the gap cost something. A row whose reasoning is a vibe gets picked late and implemented narrowly.
- **Find the SEED before spec'ing a greenfield design.** Grep for a partial implementation — an existing seam, interface, or constant the work should EXTEND — and name it in `foreman_note` ("extend the existing decision-point seam, do not fork a second abstraction beside it"). Searching first is also what tells you the gap is real rather than already solved.
- **Slice large rows deliberately and name the start slice in `foreman_note`.** Split into an ordered landing sequence (package → hot paths → harness → remainder) with each slice independently landable, and state which slice to begin with, so one tick cannot drown and the next agent does not attempt the whole refactor at once.
- **Acceptance tests must be observable, each one on its own line** — a real-time budget, an exact ordering, a count, a fail-closed exit code. "Works correctly" is not a criterion.
- **After appending, validate with the owning project's OWN gate** and confirm the row's `status` sits inside that board's vocabulary — an off-vocabulary status is invisible to the dispatcher and parks the row forever.
- **Commit PATH-LIMITED, then check the arithmetic:** `git add <board file>` and `git diff --cached --numstat` must equal exactly the expected insertions. Extra changed lines mean a concurrent foreman's rewrite of other rows got swept into your commit.
  - **When the arithmetic is wrong because a sibling is mid-write, stage only YOUR hunk — do not wait and do not commit the whole file.** A live foreman tick edits the board concurrently; a pure append then shows as `+N/-1` and a plain `git add` would publish their uncommitted row. Dump the diff, keep only the hunk containing your own row id, apply it to the index, and leave their edit sitting in the working tree for them to commit: `git diff -- <board> > /tmp/b.diff`, filter the hunks in Python keeping the one whose lines mention your id, `git apply --cached /tmp/mine.diff`, then verify `git diff --cached --numstat` reads exactly `1 0`. Confirm afterwards that their row is still present in the worktree — you are a guest in that file, not its owner.
  - Polling for the sibling to settle does not work in practice (a foreman tick can hold an uncommitted edit for many minutes); the hunk-filter is the procedure, not a fallback.
- **`[ci skip]` for board-only changes** — and never bundle a board chore with implementation commits: a `[ci skip]` token in a pushed HEAD commit suppresses run creation for the ENTIRE push.
- **Push, then confirm the lane will wake.** A board write arms a per-project `board_wake` event a few minutes later; grep the events table for the project name rather than assuming the commit alone scheduled the work.

When the owning lane cannot run yet (host over its load threshold, no free slot), the row is still the correct deliverable — arm the lane with the levers in `scheduler-lane-gate-ops` / `coding-hermes-lane-ops` and say plainly that it is filed-but-not-yet-ticking instead of implying work has started.

## Always-on rules
- **Every PRD carries ACCEPTANCE CRITERIA.** No exceptions, including the tool-prd-deep template docs — the AC block (AC-n, one per story minimum, proof-typed T/C/M, at least one anti-gaming row) sits above the success criteria and transfers verbatim into the board row's `acceptance_criteria` and the worker brief.
- "A PRD for each" = one file per item; "the pool / expanded list" = ONE combined PRD, grouped by destination project.
- Deliverables are artifacts, not chat prose: attach HTML with `MEDIA:/abs/path`; keep files in `<repo>/docs/prd/` with stable basenames so later references resolve.
- Depth means value analysis, user stories, success criteria, risks — never padding.
- Place each doc where the owning thread will find it, and say plainly when a repo is local-only (no remote) so the publish state is visible.
- When the user is still reviewing items, file only what he approved, and never start building in parallel with the thread that owns the work.
- New tool lines need a destination decision (reuse a dormant chain vs bootstrap a new one): state both costs before asking. Make it the FIRST board row of every tool in the line (`<TOOL>-001 DECISION`) and have every other tool's first row depend on it — one decision then unblocks the whole line at once.
- **Approval wave pattern:** every approval the user gives produces, in the same turn: the per-item board breakdown (dependency-chained, `<TOOL>-00N`, one row per work item and per integration hook), a memory-namespace row carrying approval + the design decisions taken + open questions, and a short chat report. Never let an approved item sit unfiled.
- Cut scope on request: when told an item is deferred, mark it deferred in the doc header AND the board status, and keep the PRD as the spec of record so activation is a status flip.
- When the user asks "questions on how to deploy it", answer with a **deployment model plus explicit open decisions**: where it runs (per-box vs central, and why), how it is launched (unit type, privileges, what it cannot see without them), lifecycle (retention, rotation, self-watchdog, gap honesty), rollout gates (prove the budget/overhead on one box before the next), and a short numbered list of decisions with defaults he can accept or override. Deployment questions are answered with a plan, not a paragraph.
- **Status roll-ups** ("what did I approve, what did I delay, where is progress") get three buckets, never one list: APPROVED (board rows filed, count them, and name the gate that is holding them), DEFERRED (marked `deferred` in doc header AND row status), AWAITING-DECISION (spec delivered, nothing filed — say so plainly rather than implying work started). Then name the ONE decision that unblocks the most items, since a batch usually shares a single gate. Report progress from the owning thread's own board (complete/pending counts + what is queued next) rather than restating your filings, and flag any delivered work that exists only on a local-only repo (no remote) as a durability gap — verified work with no off-box copy is a finding, not a detail.
